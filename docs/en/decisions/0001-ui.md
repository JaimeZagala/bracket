# 0001 — Interface framework

- **Status:** proposed, awaiting the author's decision.
- **Date:** 2026-10-15.
- **Measurement context:** machine A (Intel Core i7-13620H, 32 GB, integrated Intel UHD GPU, Windows 11 build 26200, two monitors: 1920×1080 at 125 % and 2560×1440). Rust 1.99.0, workspace release profile. Method in [measurements.md](../measurements.md).

## Context

The plan sets egui + eframe (glow backend) as the only provisional decision, to be validated in Phase 0 against at least one alternative. The requirements that weigh most: startup < 150 ms, exe < 15 MB, idle RAM < 80 MB with 10 tabs, smooth scrolling with 1M lines, IME, and the interface kept behind a thin layer.

## Options evaluated

1. **egui 0.36.2 + eframe, glow backend (OpenGL)**: the full editor prototype (`bracket-ui`).
2. **iced 0.14.0, wgpu renderer**: comparable prototype in `experiments/ui-iced` (loads the file on a thread, paints only the visible lines on a `canvas` and scrolls; no editing).
3. **iced 0.14.0, tiny-skia renderer** (software, no GPU): the same prototype.

Slint and a custom layer on winit were ruled out without a prototype: Slint does not make custom painting easy (the editor would have to use its `TextEdit` or a custom renderer), and a custom layer on winit means writing text layout, IME and accessibility from scratch.

## Measurements

Size and memory with an empty window; startup = launch → first frame with the content on screen. The first run after a build (Windows Defender scan) is excluded from the medians.

| | egui + glow | iced + wgpu | iced + tiny-skia |
|---|---|---|---|
| Executable size | 5.53 MB (with core and editor) | 6.75 MB | 2.88 MB |
| Startup, empty window (no background load) | 143 ms | 237 ms | 78 ms |
| Startup, 1M-line file (no background load) | 263 ms | 329 ms | 209 ms |
| Startup, empty window (interleaved, background load) | 291 ms | 395 ms | 132 ms |
| Startup, 1M lines (interleaved, background load) | 409 ms | 532 ms | 382 ms |
| Idle private memory, empty window | 28–40 MB | 104 MB | 8 MB |
| Idle private memory, 1M lines | 88 MB | 165 MB | 67 MB |
| CPU per scrolling frame, 1000×700 | 3.8 ms | 3.3 ms | 8.6 ms |
| CPU per scrolling frame, maximized | 4.2 ms | 3.4 ms | 14.8 ms |
| Frames per second while scrolling, maximized | ~100 (vsync) | ~100 (vsync) | 66 (no vsync, CPU-bound) |
| Clean release build | ~90 s | 121 s | 74 s |

"No background load": separate measurements at a quiet moment. "Interleaved": each round runs the three programs back to back, so the machine's background load (Teams, Visual Studio, browser; 12–43 % CPU) affects them equally; absolute values are worse, the comparison is the valid part. Scrolling moves one page per frame for 300 frames over the 1M-line file; CPU per frame = process CPU of the scroll run minus that of a startup run, divided by 300. Which monitor Windows uses for the maximized window was not checked; ~100 fps with vsync suggests a refresh rate of about 100 Hz.

## Qualitative findings

**egui + glow**

- For a custom editor widget, egui offers what is needed through its public API: keyboard, mouse, clipboard and IME events (`ImeEvent::Preedit/Commit`), IME window placement (`IMEOutput`), text layout and measurement (`Galley`: position ↔ char) and focus locking for Tab and arrows.
- Built-in accessibility through accesskit (+0.3 MB, no measurable startup cost).
- Startup of an empty window (~140 ms without load) is already close to the 150 ms budget: about 125 ms are window, OpenGL context and first frame creation inside eframe.
- eframe's wgpu backend (the default since 0.36) is much worse than glow on this machine: 9.7 MB, 264 ms and 244 MB.
- `f32` coordinates: a pixel-based `ScrollArea` loses precision (about 2 px) with 1M lines. A custom line-based scroll solves it, as the iced prototype does.
- The egui part of a scrolling frame costs 0.4 ms of CPU (headless benchmark); the rest up to ~4 ms (OpenGL rendering, driver, event loop) has not been broken down.

**iced 0.14**

- Many API changes compared with older documentation (`application` builder, `canvas::Program::update` returns `Option<Action>`, `keyboard::listen`...). Without the executor feature (`thread-pool`), `Task::perform` is silently dropped.
- A `canvas` cannot request IME or measure text: an editor needs a custom `Widget` with the `advanced` feature. IME exists (`InputMethod`, over-the-spot preedit) but only `text_input`, `text_editor` and `combo_box` use it.
- No accessibility: no iced 0.14 crate depends on accesskit.
- Text through cosmic-text: on first use it loads and parses every system font; the default monospace family ("Noto Sans Mono") does not exist on Windows and Consolas must be set by hand; lines with CJK characters sit 1–2 px off the ASCII baseline.
- tiny-skia rasterizes on the CPU: the cost per frame grows with the pixel count (8.6 → 14.8 ms when maximized) and there is no vsync. On a 4K monitor or on battery it would be worse; not measured.
- wgpu offers no advantage over egui + glow in any measurement.

## Recommendation

**Keep egui + eframe with glow.**

- It is the only option that already works for a real editor (not a viewer): IME, selection, clipboard, undo and accessibility, through a public API and without low-level widgets.
- Against iced + wgpu it wins in everything measured (startup, memory, size) and ties on scrolling.
- iced + tiny-skia wins on startup (about 60 ms without load), size and memory, but pays with CPU on every frame (growing with resolution), has no accessibility and needs the editor built as a low-level widget. It is a worse bet for an editor used for hours on large monitors.

**Accepted risk:** the 150 ms startup budget is at the limit (~140 ms without load, more when the machine is busy). Proposal for Phase 1:

1. Profile eframe startup (OpenGL context creation, font loading, first frame) and try `NativeOptions` settings (vsync, multisampling, depth buffer), measuring each change.
2. Always measure startup, locally or in continuous integration, to catch regressions.
3. If no margin is gained, revisit the budget with data (e.g. < 150 ms warm without background load, instead of cold) or reopen this decision.

The interface stays behind a thin layer: the whole model (buffer, selections, movement, document) lives in `bracket-core`, without egui; `bracket-ui` only translates events and paints.

## Consequences

- If approved: `experiments/ui-iced` is removed (it stays in the history, commit `chore(experiments): add iced 0.14 comparison prototype`) and this decision becomes "accepted".
- If iced + tiny-skia is chosen: `bracket-ui` must be rebuilt as a custom iced widget (`advanced`), accessibility must be solved another way, and the 4K cost must be measured before going further.
