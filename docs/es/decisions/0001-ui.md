# 0001 — Framework de interfaz

- **Estado:** aceptada el 2026-10-15: egui + eframe con backend glow.
- **Fecha:** 2026-10-15.
- **Contexto de medición:** equipo A (Intel Core i7-13620H, 32 GB, GPU integrada Intel UHD, Windows 11 build 26200, dos monitores: 1920×1080 al 125 % y 2560×1440). Rust 1.99.0, perfil release del workspace. Método en [measurements.md](../measurements.md).

## Contexto

El plan fija egui + eframe (backend glow) como única decisión provisional, a validar en la Fase 0 frente a al menos una alternativa. Requisitos que más pesan: arranque < 150 ms, exe < 15 MB, RAM en reposo < 80 MB con 10 pestañas, scroll fluido con 1M de líneas, IME, y que la interfaz quede detrás de una capa fina.

## Opciones evaluadas

1. **egui 0.36.2 + eframe, backend glow (OpenGL)**: el prototipo completo del editor (`bracket-ui`).
2. **iced 0.14.0, renderer wgpu**: prototipo comparable en `experiments/ui-iced`, ya eliminado (abre el fichero en un hilo, pinta solo las líneas visibles en un `canvas` y hace scroll; sin edición).
3. **iced 0.14.0, renderer tiny-skia** (por software, sin GPU): el mismo prototipo.

Slint y una capa propia sobre winit se descartaron sin prototipo: Slint no permite pintar a medida con facilidad (habría que hacer el editor con su `TextEdit` o con un renderer propio) y una capa propia sobre winit supone escribir maquetación de texto, IME y accesibilidad desde cero.

## Mediciones

Tamaño y memoria con la ventana vacía; arranque = lanzamiento → primer frame con el contenido en pantalla. La primera ejecución tras compilar (análisis de Windows Defender) se excluye de las medianas.

| | egui + glow | iced + wgpu | iced + tiny-skia |
|---|---|---|---|
| Tamaño del exe | 5,53 MB (con el núcleo y el editor) | 6,75 MB | 2,88 MB |
| Arranque, ventana vacía (sin carga de fondo) | 143 ms | 237 ms | 78 ms |
| Arranque, fichero de 1M líneas (sin carga de fondo) | 263 ms | 329 ms | 209 ms |
| Arranque, ventana vacía (intercalado, con carga de fondo) | 291 ms | 395 ms | 132 ms |
| Arranque, 1M líneas (intercalado, con carga de fondo) | 409 ms | 532 ms | 382 ms |
| Memoria privada en reposo, ventana vacía | 28–40 MB | 104 MB | 8 MB |
| Memoria privada en reposo, 1M líneas | 88 MB | 165 MB | 67 MB |
| CPU por frame con scroll, 1000×700 | 3,8 ms | 3,3 ms | 8,6 ms |
| CPU por frame con scroll, maximizada | 4,2 ms | 3,4 ms | 14,8 ms |
| Frames por segundo con scroll, maximizada | ~100 (vsync) | ~100 (vsync) | 66 (sin vsync, limitado por CPU) |
| Compilación release limpia | ~90 s | 121 s | 74 s |

"Sin carga de fondo": mediciones por separado en un momento de poca actividad. "Intercalado": cada ronda ejecuta los tres programas seguidos, para que la carga de fondo del equipo (Teams, Visual Studio, navegador; 12–43 % de CPU) les afecte por igual; los absolutos son peores, la comparación es la válida. El scroll avanza una página por frame durante 300 frames sobre el fichero de 1M líneas; CPU por frame = CPU del proceso en la prueba de scroll menos la de una prueba de arranque, dividido entre 300. No se ha comprobado en qué monitor abre Windows la ventana maximizada; los ~100 fps con vsync indican un refresco de unos 100 Hz.

## Hallazgos cualitativos

**egui + glow**

- Para un widget de editor propio, egui da lo necesario sin salir de su API pública: eventos de teclado, ratón, portapapeles e IME (`ImeEvent::Preedit/Commit`), posición de la ventana del IME (`IMEOutput`), maquetación y medición de texto (`Galley`: posición ↔ carácter) y bloqueo de foco para Tab y flechas.
- Accesibilidad con accesskit integrada (+0,3 MB, sin coste de arranque medible).
- El arranque de una ventana vacía (~140 ms sin carga) ya roza el presupuesto de 150 ms: unos 125 ms son la creación de ventana, contexto OpenGL y primer frame dentro de eframe.
- El backend wgpu de eframe (el predeterminado desde 0.36) es mucho peor que glow en este equipo: 9,7 MB, 264 ms y 244 MB.
- Coordenadas `f32`: un `ScrollArea` basado en píxeles pierde precisión (unos 2 px) con 1M de líneas. Se resuelve con un scroll propio basado en líneas, como hace el prototipo de iced.
- La parte de egui de un frame con scroll cuesta 0,4 ms de CPU (benchmark sin ventana); el resto hasta ~4 ms (renderizado OpenGL, driver, bucle de eventos) no se ha desglosado.

**iced 0.14**

- Muchos cambios de API respecto a la documentación anterior (constructor de `application`, `canvas::Program::update` devuelve `Option<Action>`, `keyboard::listen`...). Sin el feature de executor (`thread-pool`), `Task::perform` se descarta en silencio.
- Un `canvas` no puede pedir IME ni medir texto: un editor necesita un `Widget` propio con el feature `advanced`. El IME existe (`InputMethod`, preedición "over-the-spot"), pero solo lo usan `text_input`, `text_editor` y `combo_box`.
- Sin accesibilidad: ningún crate de iced 0.14 depende de accesskit.
- Texto con cosmic-text: la primera vez carga y analiza todas las fuentes del sistema; la familia monoespaciada por defecto ("Noto Sans Mono") no existe en Windows y hay que fijar Consolas a mano; las líneas con caracteres CJK quedan 1–2 px desplazadas respecto a las ASCII.
- tiny-skia rasteriza en la CPU: el coste por frame crece con los píxeles (8,6 → 14,8 ms al maximizar) y no hay vsync. En un monitor 4K o con batería sería peor; no se ha medido.
- wgpu no aporta nada frente a egui + glow en ninguna medida.

## Recomendación

**Mantener egui + eframe con glow.**

- Es la única opción que ya cumple con un editor real (no un visor): IME, selección, portapapeles, deshacer y accesibilidad, con API pública y sin widgets de bajo nivel.
- Frente a iced + wgpu gana en todo lo medido (arranque, memoria, tamaño) y empata en scroll.
- iced + tiny-skia gana en arranque (unos 60 ms sin carga), tamaño y memoria, pero paga con CPU en cada frame (que crece con la resolución), sin accesibilidad y con el editor por hacer como widget de bajo nivel. Es una apuesta peor para un editor que se usa horas en monitores grandes.

**Riesgo que se acepta:** el presupuesto de arranque de 150 ms queda al límite (~140 ms sin carga, más con el equipo ocupado). Propuesta para la Fase 1:

1. Perfilar el arranque de eframe (creación del contexto OpenGL, carga de fuentes, primer frame) y probar opciones de `NativeOptions` (vsync, multimuestreo, búfer de profundidad) midiendo cada cambio.
2. Medir siempre el arranque en la integración continua o en local para detectar regresiones.
3. Si no se gana margen, revisar el presupuesto con datos (p. ej. < 150 ms en caliente sin carga de fondo, en lugar de en frío) o reabrir esta decisión.

La interfaz sigue detrás de una capa fina: todo el modelo (buffer, selecciones, movimiento, documento) está en `bracket-core`, sin egui; `bracket-ui` solo traduce eventos y pinta.

## Consecuencias

- egui + eframe (glow) es el framework de interfaz del proyecto. La interfaz sigue detrás de una capa fina para poder cambiarla si una medición futura lo justifica.
- `experiments/ui-iced` se ha eliminado del repositorio; el código queda en el historial (commit `61c1712`, `chore(experiments): add iced 0.14 comparison prototype`).
- Carencia de egui detectada tras la comparación: de serie solo incluye las fuentes Hack, Ubuntu y emoji, sin caracteres CJK (chino, japonés, coreano), que hoy se ven como cuadros. En la Fase 1 hay que cargar fuentes del sistema (una monoespaciada como Consolas o Cascadia Mono y una CJK de respaldo) midiendo su coste en arranque y memoria. Anotado en la deuda técnica de [architecture.md](../architecture.md).
- Trabajo para la Fase 1: el plan de arranque de la sección anterior.
